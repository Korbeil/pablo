YOLO mode

In YOLO mode PABLO does what you'd do after each plan: it has the plan implemented, then runs /pablo-commit-and-pr itself. A task goes from issue to draft pull request, and through CI fixes and review feedback, with nobody at the keyboard. It is off unless you turn it on, per project or per task.

Nobody reviews the plan and nobody confirms the commit: what the agents decide is pushed to your pull request. The pull request stays a draft until CI is green, and a person still reviews and merges it. Start with a project where that's fine.

How it runs

The agents don't change: each state still launches its read-only analyst, which writes a plan. In YOLO mode two more runs follow, in the analyst's own session, so they start from its plan:

  1. yolo-implement, once the analyst has finished: your runtime's own build agent (OpenCode's build, Claude Code's and Copilot's default agent, not a PABLO agent) executes the plan, adds or updates tests and runs the project's QA. It doesn't commit.
  2. yolo-commit, once the implementation has finished: the same session runs /pablo-commit-and-pr, from the very text of the command, so it commits, pushes, opens the draft pull request if there is none (or pushes to the existing one) and moves the task to draft. When there is nothing to commit, it stops, as the command always does.

This happens after every analyst: task-analyst (in-progress), ci-analyst (ci-red), pr-feedback (request-changes) and task-feedback (testing-failed). So a red CI is fixed and pushed, review threads are addressed and pushed, and the poller carries on as usual: CI green, pull request ready, review.

With Orca, each run opens its own terminal next to the plan (pablo:yolo-implement, pablo:yolo-commit), and the analyst runs as a one-shot command instead of the OpenCode TUI: the TUI only ends when you quit it, which would hold the next step back. With OpenChamber the analyst runs in OpenChamber as usual and the two follow-ups run headless on its session (OpenChamber can't approve a tool call by itself). Headless, everything runs in the background, logged under ~/.pablo/agents/logs/.

Turn it on

For every task of a project, or for all projects in ~/.pablo/config.yaml:

yolo:
  enabled: true
  max_rounds: 5      # optional, default 5

For one task, whatever its project says:

  • pablo task:start <issue-url> --yolo, or --no-yolo to keep a task of a YOLO project manual;
  • the YOLO mode checkbox of the dashboard's New task form. In prompt mode it shows the project's setting; untouched in issue mode, the issue's project decides;
  • on a running task: pablo task:yolo on|off|project [<branch>] (project hands the choice back to the project). It applies from the next analyst; a run already going finishes, but no commit follows an implementation once YOLO is off.

A YOLO task shows a ⚡ badge on the dashboard, with the step running (implement, commit) while there is one. While a step runs, the task isn't listed as waiting for you.

Limits

  • yolo.max_rounds: each implementation counts as one round. Past the limit, the next plan waits for you as usual (and the poll log says so). pablo task:yolo starts the count again.
  • No commit from waiting: pause a task and an implementation in flight ends without a commit; its changes stay in the worktree.
  • Stuck runs: a step whose watcher died is considered finished by the poller about an hour after it started, and the next step goes on.
  • Models: yolo-implement and yolo-commit are agent keys of models, so the implementation can run on a stronger model than the analysts.

What the runs may not do

Both runs approve their own tool calls, except these, refused whatever the runtime (raw and rtk-prefixed): changing the git identity (git config, git -c user…), switching, resetting, rebasing, stashing or tagging, deleting branches, any GitHub write but creating the draft pull request (gh pr comment, edit, review, ready, merge, close, gh issue, gh api…), and every Jira, Confluence and Linear command. Their prompts say the same.

  • Claude Code: claude -p --resume <session> --permission-mode acceptEdits, with the build tools allowed and the list above as --disallowedTools.
  • Copilot CLI: copilot --resume=<session> --allow-all-tools, with the list as --deny-tool (a deny always wins).
  • OpenCode: opencode run -s <session> --agent build --auto. opencode run takes no per-run rules: --auto approves everything your own OpenCode configuration doesn't deny, so the list above only reaches it through the prompt. Add the denies you care about to the permission of your OpenCode configuration, which --auto keeps.

Everything else stays as on What PABLO may change: the commits are /pablo-commit-and-pr's, pushed with --force-with-lease, under your own git identity, and the pull request is only ever created as a draft.
