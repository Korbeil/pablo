Development

How the PABLO repository is organised, how the engine is built, and how to run the quality checks before sending a change. The engine is a Symfony application in app/; quality tools run through Castor.

Repository layout

pablo/
├── app/                  # the Symfony application (Composer package "pablo")
│   ├── bin/pablo         # the pablo command (PABLO commands only); the binary's entry point
│   ├── bin/console       # framework maintenance: cache:clear, lint:twig, debug:router…
│   ├── box.json          # how the binary's phar is built (Box)
│   ├── public/index.php  # front controller for a regular PHP server (pablo web does not use it)
│   ├── config/           # bundles, services, routes, packages/
│   ├── src/              # the engine
│   ├── templates/        # Twig: dashboard pages and components
│   ├── assets/           # dashboard JS, CSS, fonts, icons, vendored libraries
│   └── tests/            # PHPUnit, mirroring src/
├── examples/             # example global and project configuration (config.yaml is bundled in the binary)
├── opencode/             # agent templates, the commit command, the skill (the single source for every runtime)
├── systemd/, launchd/    # scheduler and dashboard service definitions, written by pablo system:install
├── site/                 # this website; site/installer is the curl | bash installer, served at /installer
└── castor.php            # quality and build tasks

The binary is the same tree packed into one file. Nothing is ever written into the repository (or the binary) at runtime: rendered agents go to ~/.pablo/runtime/, and the only other files outside ~/.pablo/ are the links, service files and PATH block pablo system:install creates.

Engine modules

Namespaces mirror folders (Pablo\ is app/src/).

Architecture notes

  • One kernel, three entry points. bin/pablo, bin/console and the dashboard share one FrameworkBundle kernel. From a checkout its container is cached in app/var/cache/<env> and PABLO_ENV defaults to dev, so the cache is revalidated after a git pull. From the binary (a read-only phar) it is cached in ~/.pablo/cache/container/<version>/<env>-<hash> and PABLO_ENV defaults to prod: a new version never reuses an old container.
  • Bundled files are read-only. Templates, service files and the example config may sit inside the binary: read them through PabloPaths::resourcesDir(), list them with Support\Files::list() (glob() sees nothing inside a phar), and write whatever is rendered from them under ~/.pablo/runtime/.
  • The dashboard runs on php -S (Web\PhpServer), 127.0.0.1 only, four workers. The binary's micro SAPI has no php -S, so the binary carries a static PHP CLI (bin/php in the phar); pablo web extracts it with a plain copy of the phar (the bytes after the micro prefix, which a regular PHP can read) and a router, then serves the compiled assets from inside the phar through public/index.php. Never fork a process that already reads the phar: the children share its file handle, and concurrent reads corrupt each other.
  • Never resolve a PABLO_* variable (or HOME) when the container is compiled: the value would be frozen into the cache. Store and Agents resolve their paths in their constructors for this reason.
  • pablo --help lists PABLO commands only: the console application collects the pablo.command tag, not console.command.
  • Add a state: a case in Domain/State.php and a row in StateMachine::states(). Always change state through StateMachine::enterState(), never by setting the field.
  • Add an issue tracker: implement ProviderInterface and register it in ProviderRegistry.
  • Terminal and dashboard can't drift: both render the same value objects (PrBadge, AgentActivity) and use the same rules (Listing::isWaitingForFeedback(), Listing::stateRank()).
  • The dashboard never calls external tools while rendering: it reads the poller's DisplayCache. Analytics come from AnalyticsAggregator, shared with pablo stats.
  • Portability: the engine runs on Linux and macOS. tests/PortabilityTest.php fails if src/ mentions systemctl, journalctl, /etc/, /proc/ or /opt/, except in Install/Scheduler/SystemdScheduler.php, which only ever runs on Linux.

Quality checks

Run from the repository root, with the global Castor binary. The PHP tools are downloaded on first use.

castor qa:test                          # PHPUnit
castor qa:phpstan                       # static analysis, level 8
castor qa:cs-fixer                      # fix coding style (@Symfony + @Symfony:risky)
castor qa:cs:check                      # check only (what CI runs)
castor qa:twig-cs-fixer                 # Twig templates
(cd app && composer exec phpunit tests/StateMachineTest.php)   # one test file
php app/bin/console lint:twig app/templates

PHPStan runs at level 8 over src, tests, config and public. Raise the level by fixing what it reports, never by ignoring errors or adding them to the baseline. php-cs-fixer covers exactly the paths listed by the Finder in app/.php-cs-fixer.php (the castor tasks pass none): a new top-level folder is added there.

CI (.github/workflows/ci.yml) runs the tests, PHPStan and the coding-style check on every push to main and every pull request, from a checkout. .github/workflows/binary.yml builds the binaries (see below).

The standalone binary

What users install is one file per platform: the application packed into a phar by Box (app/box.json), appended to a static PHP built by static-php-cli (micro.sfx). It carries everything: vendor/ without dev dependencies, the compiled dashboard assets (asset-map:compile), the agent templates, the service files and examples/config.yaml. Its version is the first 7 characters of the commit SHA, and a checkout reports dev.

castor build:binary                          # dist/pablo.phar (needs a PHP to run)
castor build:binary --micro=buildroot/bin/micro.sfx --php-cli=buildroot/bin/php --spc=spc
                                             # + dist/pablo, the standalone binary

The task builds from a copy in dist/stage/, so your app/vendor/ keeps its dev tools and no compiled assets land in app/public/assets/ (they would shadow the dev AssetMapper). Build a micro.sfx and a PHP CLI once with static-php-cli (spc build <extensions> --build-micro --build-cli; the task prints the commands). The CLI is embedded for pablo web; without --php-cli the dashboard needs a php on the PATH. The extensions are phar, ctype, iconv, mbstring, tokenizer, filter, posix, pcntl, dom, xml, zlib, openssl. OPcache is not enabled in the binary: with PHP 8.5's micro, opcache.enable_cli=1 crashes at startup.

.github/workflows/binary.yml builds pablo-linux-x86_64, pablo-linux-aarch64, pablo-macos-arm64 and pablo-macos-x86_64 on every pull request (nothing is published) and smoke-tests each one (on Linux in a debian:stable-slim container without PHP), dashboard included, with parallel requests.

Releasing

castor release:create              # release main's last commit, flagged latest
castor release:create --no-latest  # publish it without making it the one users get
castor release:list                # the last 10 releases (--limit to see more)

A release is named after the last commit on main: the first 7 characters of its SHA (tag and title), which is also exactly what its binaries report with pablo --version (the release job checks it). The task starts the Binary workflow on main; only once the four builds pass does the workflow create the release, with the binaries and sha256sums.txt, so the release the installer and pablo update pick (the one flagged latest) always has its binaries. It needs the gh CLI, logged in with write access to the repository, and refuses a commit that already has a release. A release published without the latest flag can still be installed by name: pablo update <release>.

Tests

  • Tests mirror the source tree: app/src/Store/Store.php is tested by app/tests/Store/StoreTest.php.
  • The engine uses dependency injection everywhere. Collaborators that touch the outside world sit behind interfaces (GhPrInterface, GitRepoInterface, ProcessRunnerInterface, ProviderRegistryInterface, AnalyticsInterface, AgentLauncherInterface), with fakes beside the tests: FakeAgents, FakeGit, FakeGhPr, FakeProcessRunner, StubProviders, FakeAnalytics.
  • FakeAgents is injected wherever a real agent launcher could be reached, so a test can never start a real opencode run, claude -p or copilot -p (a real, paid model call).
  • tests/Command/CommandTestBed.php wires the fake graph for command tests; tests/EngineGraph.php does the same for the poller, listing and dispatcher.
  • A test that boots the kernel must use the RestoresErrorHandlers trait around the boot, or PHPUnit flags it as risky.

Dashboard assets

AssetMapper and an importmap: no Node, no build step, nothing fetched at runtime.

php app/bin/console importmap:install            # after changing app/importmap.php
php app/bin/console ux:icons:import lucide:name  # add an icon, then commit it
  • app/assets/vendor/ must stay committed: neither the binary build nor an install runs importmap:install, so a missing file means a dashboard without JavaScript. (The root .gitignore only ignores /app/vendor/ for that reason.)
  • Icons are Lucide icons committed in app/assets/icons/, with online downloads disabled.
  • The fonts (Josefin Sans, JetBrains Mono, SIL Open Font License) are committed in app/assets/fonts/.
  • app/assets/styles/app.css themes Bulma after this website. Colour classes returned by TaskView and RebaseLogView (is-danger, is-success…) are mapped to soft tones in both themes; never use a bare tag is-light or is-grey (a test guards it).

This website

The site lives in site/: the home page and assets as plain files, and one HTML fragment per documentation page in site/content/, listed in site/content/nav.yaml. A small PHP builder in site/build/ wraps each page in the layout, adds heading anchors and the “On this page” column, highlights code, checks every internal link, and writes the search index.

castor site:build   # build into _site/
castor site:serve   # build and preview on http://127.0.0.1:8000

Inside a page, link to another page with href="page:states#reviews" (a typo fails the build), to a repository file with href="repo:app/src/Poller/Poller.php", and to a site asset with asset:assets/dashboard.png. Callouts are <aside class="callout note|tip|warning">. Pushing to main deploys the site with GitHub Pages.

Git discipline

PABLO's own agents never commit or push on their own initiative; the only sanctioned paths are an explicit request from you, or /pablo-commit-and-pr. Contributions follow the same spirit: changes are delivered as a working tree or a pull request, and you decide when they land.
