Installation

PABLO is a single binary: no PHP, no Composer. Install it with one script, then let pablo system:doctor tell you which tool is missing or logged out. It takes a minute on Linux (x86_64, aarch64) or macOS (Apple silicon, Intel).

Prerequisites

Start with the minimum below. Everything else depends on where your projects live, and you can add it later, when you add the project that needs it.

The minimum

  • git: every task is a branch and a worktree.
  • An agent runtime that runs the agents: OpenCode set up with your usual model provider (the default), Claude Code logged in to your Claude account, or GitHub Copilot CLI logged in to your GitHub account. See With Claude Code and With GitHub Copilot CLI.
  • An agent development environment, Orca or OpenChamber: where agents run and where you chat with them. Optional in theory (without one, agents run headless in the background), but that's where you'll read their work. See Choose an agent backend.
  • curl, to download PABLO. Nothing else: the binary carries its own PHP.

Then, for your projects

PABLO talks to each service through its own command-line tool, logged in once on your machine. Install the ones your projects use:

Your project uses…You needLog in once with
GitHub pull requests (every project: PABLO follows PRs and CI on GitHub, whatever the issue tracker)ghgh auth login
Jira issues, or Confluence pagesacliacli auth login (one login covers both)
Linear issueslinearsee its docs (checked with linear auth status)

GitHub Issues need nothing more than gh. More details on what each tool is used for in Providers.

No need to get it all right up front: the installer finishes with pablo system:doctor, which checks exactly the tools your projects need and tells you how to install or log in to each one.

Install

curl -fsSL https://getpablo.dev/installer | bash

The script is interactive, on Linux and macOS. It:

  1. checks that git and curl are there, and which binary your OS and processor need;
  2. looks for the agent runtimes you have (OpenCode, Claude Code, GitHub Copilot CLI) and asks which one to use;
  3. looks for the agent development environments you have (Orca, OpenChamber) and asks which one to use. It only offers the ones that can run your runtime;
  4. asks whether to install the dashboard service. If another program already uses its port (8321, or the dashboard_port of your config), it suggests the next free port and lets you type another; without a terminal it takes the suggestion. A port already used by PABLO's own dashboard (a re-install) is kept. Then it shows a summary;
  5. downloads pablo-<os>-<arch> from the latest GitHub release, checks it against the release's sha256sums.txt (a mismatch installs nothing), installs it as ~/.local/bin/pablo, then runs pablo system:install with your answers.

If it finds no agent runtime, it stops and sends you back to the prerequisites. If it finds no agent development environment, it says so with the same pointer and offers to carry on headless (the agents then run in the background) or to stop so you can install one first. Without a terminal, it carries on headless.

Every question has an option, so you can script it. Pass options after bash -s --:

curl -fsSL https://getpablo.dev/installer | bash -s -- --runtime claude-code --backend orca --no-interaction
OptionMeaning
--version <release>a release to install, by name (the short commit hash, e.g. 5b34e92), instead of the latest
--runtime <name>opencode, claude-code or copilot
--backend <name>orca, openchamber (OpenCode only) or headless
--without-webskip the dashboard service
--port <port>the dashboard's port, instead of 8321 (or the next free one)
--no-interactionnever ask: use the options, then what it detected. It is also what happens when there is no terminal

Run it again to update. It stops only when a pablo command that is not PABLO is in the way, in ~/.local/bin or on your PATH; another PABLO elsewhere on your PATH is only warned about, since it may shadow the new one. An older install made from a clone of the repository is migrated.

What pablo system:install does

The installer hands over to pablo system:install, which you can also run yourself at any time: it is safe to run again. Without options it keeps the choices already in ~/.pablo/config.yaml, or on a first install picks the tools it finds. Two options record a choice there instead: --runtime opencode|claude-code|copilot and --backend orca|openchamber|headless (the installer leaves --backend out when it only falls back to headless because it found no environment). Changing the runtime also resets default_model to a model of that runtime. --without-web skips (and removes) the dashboard service, and --port <port> records the dashboard's port (dashboard_port). It:

  1. creates ~/.pablo/ and, if you don't have one yet, a default global config in ~/.pablo/config.yaml, set to the tools you have installed (Claude Code when it finds Claude Code but no OpenCode, Copilot when it finds Copilot CLI but neither, OpenChamber when it finds OpenChamber but no Orca);
  2. makes sure ~/.local/bin/pablo is this binary and, if that directory isn't on your PATH yet, adds it (see below);
  3. renders the agents for your agent runtime, and extracts the /pablo-commit-and-pr command and the pablo-task skill, into ~/.pablo/runtime/;
  4. links them into ~/.config/opencode/ (OpenCode), ~/.claude/ (Claude Code) or ~/.copilot/ (Copilot);
  5. writes and starts the background scheduler, which runs PABLO every 5 minutes, and the dashboard on http://127.0.0.1:8321 (restarting it, so it runs the new binary);
  6. runs pablo system:doctor and prints your next steps.

Your own OpenCode, Claude Code and Copilot files are never touched. PABLO only creates new symlinks, all pointing into ~/.pablo/runtime/, and refuses to replace any file in ~/.config/opencode/, ~/.claude/ or ~/.copilot/ that isn't already one of its links. The same goes for the scheduler files: one without PABLO's marker: line is never overwritten.

From a checkout (contributors)

Working on PABLO itself? Clone the repository and run it from there, with PHP 8.4.1+ (extensions ctype, filter, iconv, mbstring, phar and zlib; pcntl and posix are optional) and Composer: php app/bin/pablo is the same application as the binary. pablo system:install run from a checkout writes a ~/.local/bin/pablo shim that runs php app/bin/pablo instead of copying a binary; everything else is the same.

git clone https://github.com/Korbeil/pablo
cd pablo
(cd app && composer install)
php app/bin/pablo system:install    # or: castor install

To build the binary yourself, see Development.

The pablo command on your PATH

When ~/.local/bin isn't on your PATH already, the installer appends a short block, between # >>> pablo >>> and # <<< pablo <<< markers, to ~/.zshrc (zsh) or ~/.bashrc (bash; ~/.bash_profile on macOS). For fish it writes ~/.config/fish/conf.d/pablo.fish instead. Open a new terminal afterwards. Running the installer again never adds the block twice, and pablo system:uninstall removes it. With another shell, the installer prints the line to add yourself.

Check your setup

pablo system:doctor   # one line per check: ✅ ready, ❌ missing or logged out
pablo system:setup    # the same checks as a wizard, one fix at a time

system:setup stops at the first problem and prints the exact command to install or log in to the tool. Fix it, run pablo system:setup again, and it moves on to the next check. Tracker tools (acli, linear) are only checked once a project uses them.

The doctor also checks that the installed agents are up to date: ~/.config/opencode/agents/ under OpenCode; ~/.pablo/runtime/claude/agents.json, the ~/.claude/agents/pablo-*.md files, the command and the skill under Claude Code; the agent files and skills in ~/.copilot/ under Copilot. If one is reported stale, run pablo system:generate-agents.

With Claude Code

Set agent_runtime: claude-code and a Claude model in ~/.pablo/config.yaml (a first install does it when it finds claude but no opencode), then run pablo system:install again, or let it set both for you with pablo system:install --runtime claude-code:

agent_runtime: claude-code
default_model: sonnet        # or opus, haiku, or a full model id
  • Prerequisite. The claude command, logged in: the doctor runs claude auth status. Install it with curl -fsSL https://claude.ai/install.sh | bash.
  • What is installed. ~/.pablo/runtime/claude/agents.json holds the five agents; the installer links ~/.claude/commands/pablo-commit-and-pr.md and ~/.claude/skills/pablo-task.
  • Your own sessions. The installer also links the agents into ~/.claude/agents/ as pablo-<agent>, so they appear in /agents and the @ picker. PABLO's own launches still pass agents.json with --agents; only those enforce the per-command shell denies.
  • Backend. Use Orca, or no backend (headless). OpenChamber can't run Claude Code; the doctor reports it.

With GitHub Copilot CLI

Set agent_runtime: copilot and a Copilot model in ~/.pablo/config.yaml (a first install does it when it finds copilot but neither opencode nor claude), then run pablo system:install again, or let it set both for you with pablo system:install --runtime copilot:

agent_runtime: copilot
default_model: claude-sonnet-5.5   # or another Copilot model id, e.g. gpt-5.3-codex
  • Prerequisite. The copilot command (npm install -g @github/copilot), logged in once with copilot login. The doctor only runs copilot --version: Copilot has no non-interactive login check, so a run fails if you're logged out.
  • What is installed. The five pablo-<agent>.agent.md files, rendered into ~/.pablo/runtime/copilot/, are linked into ~/.copilot/agents/; the pablo-commit-and-pr and pablo-task skills into ~/.copilot/skills/ (under COPILOT_HOME when set).
  • Visible on purpose. Unlike Claude Code, the agents go where your own Copilot sessions can pick them, prefixed pablo-.
  • Backend. Use Orca, or no backend (headless). OpenChamber can't run Copilot; the doctor reports it.

Switching runtime later works the same way: run pablo system:install again with --runtime (or change agent_runtime and run it without). The other runtimes' links stay in place until pablo system:uninstall; they're harmless.

Choose an agent runtime

The runtime is the program that runs the agents: OpenCode, Claude Code or GitHub Copilot CLI. The installer lists the ones it finds on your PATH and asks which to use. With a single one it takes it without asking, and with none it stops. To change it later, see With Claude Code and With GitHub Copilot CLI, or run pablo system:install again with --runtime.

Choose an agent backend

The agent backend is where PABLO's agents run, and where you open them to read their analysis or keep chatting. The installer only offers what matches your runtime: Orca, or headless, with any runtime; OpenChamber too, with OpenCode only. Run again with --backend to change it. Without a choice, a first install picks Orca by default, OpenChamber when it finds OpenChamber but no Orca. When it finds neither, agents run headless, but the backend stays Orca, so it is used as soon as you install it; choose headless explicitly to never use one. The doctor only checks the backend you use. Both run OpenCode; with Claude Code or Copilot, use Orca or headless.

Orca (default)
Agents run in Orca terminals. Orca only sees repositories registered with it, so register each project's repository once: orca repo add --path <path> (on Linux the Orca CLI is orca-ide: orca is GNOME's screen reader).
OpenChamber
Set agent_backend: openchamber in ~/.pablo/config.yaml (or export PABLO_AGENT_BACKEND=openchamber). PABLO drives it through OpenChamber's CLI, the npm package @openchamber/web (npm i -g @openchamber/web, Node.js 24.14+), which sends the sessions to the running desktop app when there is one. The desktop app installs an openchamber command too, which ignores the CLI's commands: put the CLI first on your PATH. OpenChamber works from directories, so there is nothing to register. OpenCode only: not available with agent_runtime: claude-code or copilot.
Headless
No agent development environment: agent_backend: headless (or --backend headless) runs every agent as opencode run (or claude -p, copilot -p) in the background. It is also what Orca and OpenChamber fall back to when they are unavailable or don't know a repository, so agents still run. You read their output with opencode -s <session> (or claude --resume <session>, copilot --resume=<session> in the worktree). Under OpenCode, opencode pair prints a link to OpenCode's local web interface, where every session, the agents' included, shows live: see Follow headless OpenCode runs in the browser.

More details in How it works.

The dashboard service

The installer keeps the dashboard running as a background service that restarts on its own, on http://127.0.0.1:8321. See Dashboard.

Don't want it? Answer no when the installer asks, or install (or re-install) with --without-web; this also removes a dashboard service installed before. You can still start the dashboard by hand with pablo web.

curl -fsSL https://getpablo.dev/installer | bash -s -- --without-web
# or: pablo system:install --without-web

To only stop it for now: systemctl --user stop pablo-web.service on Linux, launchctl bootout gui/$UID/com.pablo.web on macOS.

PABLO itself is portable. Only the scheduler and the dashboard service differ:

Background agents are started in a session of their own with setsid on Linux; macOS has no setsid, so PABLO uses the system perl there instead. The doctor warns when neither is on your PATH.

On Linux the installer enables lingering for your user (loginctl enable-linger), so the scheduler also starts after a reboot without you logging in.

First install on macOS

  1. Install the prerequisites, including acli auth login if you use Jira or Confluence.
  2. Run the installer and look for “com.pablo.dispatch loaded”.
  3. Run pablo system:doctor: everything should be ✅.
  4. Watch one 5-minute run: tail -f ~/.pablo/logs/dispatch.log.
  5. Try a round trip on a real project: pablo task:start …, then pablo task:list.

Update

pablo update           # or pablo system:update
pablo update --check   # only tell whether a newer release exists
pablo update 5b34e92   # install that release instead (an older one too)
pablo update --rollback  # go back to the binary the last update replaced

PABLO updates itself: it finds the release flagged latest (releases are named after the commit they were built from) and, when it is not the one you run, downloads its binary for your OS and processor with curl, checks it against the release's sha256sums.txt, runs it once, then swaps it in place of the current one (a failed check changes nothing). It then runs pablo system:install with the new binary, which picks up new agents and links and restarts the dashboard; --no-install skips that step. A dashboard you opted out of (--without-web) stays off. If the background job is running (a sync or a poll), the update first waits for it to finish, up to 10 minutes, and no new run starts until the update is done. Your choices in ~/.pablo/config.yaml and your data in ~/.pablo/ are kept. Each version compiles its own cache in ~/.pablo/cache/container/<version>/; the install removes the ones of other versions.

Rolling back

Each update keeps the binary it replaces as ~/.local/bin/pablo.previous (only one: the next update replaces it). It sits next to pablo rather than in ~/.pablo/ because only the same directory is sure to be on the same filesystem, which the swap needs to be atomic; it is a hard link where the filesystem allows, so it takes no extra space while a service still runs it. pablo update --rollback runs it once (--version), swaps it back in place under the same lock as an update, runs its system:install (keeping --without-web) and reports PABLO rolled back: <current> → <previous>. The binary it replaces becomes the previous one in turn, so a second rollback undoes the first. --no-install skips the install, --check only tells whether a previous binary is kept. Without one (a fresh install, or one that was never updated), it says so: install an older release by name with pablo update <release> instead.

The rollback is automatic when the system:install that follows an update fails: the previous binary is restored, runs system:install in turn, and the update reports PABLO rolled back: <new> → <previous> and exits with an error. pablo system:uninstall removes pablo.previous along with pablo.

Running the installer again (curl -fsSL https://getpablo.dev/installer | bash) does the same, and also takes a release with --version. The releases are listed on GitHub.

From a checkout: git pull, (cd app && composer install), then php app/bin/pablo system:install.

Migrating from a clone install

Earlier versions were installed by cloning the repository (to ~/.local/share/pablo by default) and running bin/install.sh, which wrote a ~/.local/bin/pablo shim running php …/app/bin/pablo. Run the installer above: it recognises that shim, replaces it with the binary, and pablo system:install takes over everything that install created. The links that pointed into the checkout now point into ~/.pablo/runtime/, the systemd units that were links into the checkout are written as files, and ~/.pablo/claude/agents.json moves to ~/.pablo/runtime/claude/. The checkout itself is never touched: delete it once everything works. Your config, projects and tasks in ~/.pablo/ carry over as they are.

Uninstall

pablo system:uninstall

It removes what the install created (the pablo command, the links under ~/.config/opencode/, ~/.claude/ and ~/.copilot/, including the links an old clone install made, the generated ~/.pablo/runtime/ and ~/.pablo/cache/container/, the PATH block, the scheduler and dashboard services) and keeps your data in ~/.pablo/. Delete ~/.pablo/ as well if you want a clean slate, or back it up first.
