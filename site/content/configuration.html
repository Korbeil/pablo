Configuration

PABLO reads two kinds of YAML files: one global ~/.pablo/config.yaml with your defaults, and one file per project in ~/.pablo/projects/. A project can override any default, key by key.

Global defaults

~/.pablo/config.yaml is created by the installer from examples/config.yaml. It holds the keys every project inherits, plus a few that only exist globally.

default_model: openrouter/deepseek/deepseek-v4-flash-0731
pr_description_locale: en
sync:
  strategy: rebase
  auto_apply: false
  interval_minutes: 720
state_polling:
  interval_minutes: 10
review:
  bot_whitelist: []
ci:
  ignore_checks: ["approval"]
# agent_backend: openchamber        # global only, default orca
# default_model_by_type:            # global only
#   work: anthropic/claude-opus-4

Keys a project inherits

When a project omits one of these keys, the global value applies; when the global file omits it too, the built-in default does.

KeyBuilt-in defaultMeaning
default_modelrequired somewhereModel for agents (see below)
pr_description_localerequired somewhereLanguage of the pull request descriptions /pablo-commit-and-pr writes
branch_prefixnonePrefix added to every branch name, verbatim (write the slash yourself, e.g. pablo/)
sync.strategyrebaserebase or merge
sync.auto_applyfalsefalse: sync only reports
sync.interval_minutes30How often branches are synced
state_polling.interval_minutes10How often pull requests are checked
main_update.enabledtrueKeep the main checkout up to date
main_update.interval_minutes60How often
testing.enabledtrueWhether the project has a QA step
review.bot_whitelist[]Bot accounts whose reviews count
ci.ignore_checks[]Checks to leave out of CI

If default_model or pr_description_locale isn't set anywhere (and, for the model, no default_model_by_type entry matches), loading the project fails with an error.

Global-only keys

agent_backend
orca (default) or openchamber. Also settable with the PABLO_AGENT_BACKEND environment variable. With openchamber, the doctor checks the openchamber command too. See Agent backends.
default_model_by_type
A model per project type; see below.

Choose the agent model

The model is resolved when an agent is launched, and passed to the backend as --model. The first one found wins:

  1. the project's own default_model;
  2. the entry for the project's type in default_model_by_type;
  3. the global default_model;
  4. as a last resort, the model written in the generated agent file.
# ~/.pablo/config.yaml — expensive models only on work projects
default_model_by_type:
  work: anthropic/claude-opus-4
  open-source: litellm/glm-5.3-flash
  personal: openrouter/deepseek/deepseek-v4-flash-0731

Keys must be project types (work, open-source, personal); an unknown key is an error.

Project files

One YAML file per project in ~/.pablo/projects/, any file name. Create one with pablo project:new or by hand. Every key:

name: wallet-kit              # required, unique
type: open-source             # required: work | open-source | personal

repo:
  path: ~/dev/wallet-kit      # required: the main checkout
  primary_branch: main        # required
  primary_remote: upstream    # optional, default "origin": the remote sync and new
                              # branches use, e.g. when origin is your fork

worktrees_root: ~/dev/wallet-kit-worktrees
                              # optional, default ~/.pablo/worktrees/<repo folder name>/

issue_tracker:
  provider: github            # required: github | jira | linear
  identity: your-login        # required: whose issues are "assigned to me"
                              # (informational for Jira, which uses your acli login)
  project_key: WK             # required. Jira/Linear: the issue key prefix.
                              # GitHub: the branch prefix (GitHub has no keys)
  site: acme.atlassian.net    # Jira only, optional: the Atlassian site for links
  repo: acme/upstream         # GitHub only, optional: where issues and pull requests
                              # live, when you work on a fork

confluence:
  space: PIM                  # Jira only, optional: where agents look for docs

sync:
  strategy: rebase            # rebase | merge
  auto_apply: false
  interval_minutes: 30
state_polling:
  interval_minutes: 10
main_update:
  enabled: true
  interval_minutes: 60

testing:
  enabled: true               # false: no QA step, approval is final
  failure_signal: qa-failed   # GitHub: a pull request label. Jira/Linear: an issue status.
                              # Without it, testing-failed never triggers by itself.
review:
  bot_whitelist: ["copilot-pull-request-reviewer[bot]"]
ci:
  ignore_checks: ["approval"]

startup_script: ~/scripts/pablo-setup.sh
                              # optional: bash script run once per task, next to
                              # task-analyst, in its own terminal
default_model: openrouter/deepseek/deepseek-v4-flash-0731
pr_description_locale: en
branch_prefix: pablo/

ci.ignore_checks

A list of words. Any check whose name, workflow or context contains one of them is left out when PABLO decides whether CI is red or green. Use it for checks that never finish on their own, such as CircleCI manual approval gates, which stay pending (or “action required”) forever and would otherwise keep the task in draft. It's deliberately simple: a substring match.

Startup script

startup_script runs once per task when it starts, in parallel with task-analyst, in its own terminal that stays open as a shell afterwards, so you can see its output. Use it to install dependencies or prepare the worktree. It's launched in the background and never blocks pablo task:start. It may run again if PABLO relaunches a launch that never started, so keep it safe to re-run.

Branch names

Branches PABLO creates follow a fixed pattern, lowercased:

[branch_prefix][project-key]-[issue-id]
  • Jira and Linear: the issue's key, so PIM-123 becomes pim-123.
  • GitHub: the project's issue_tracker.project_key and the issue number: project_key: WK and issue #45 give wk-45.
  • Prompt tasks: the project key and a short slug of the prompt, such as wk-fix-callback-verification. If the prompt mentions a Jira or Linear key from one of your projects, that issue's name is used instead.
  • No title is added: the name is only those parts.
  • Duplicates: if the name is already taken, PABLO tries -2, -3, … until one is free. It never reuses or overwrites a branch.

With branch_prefix: pablo/, the issue above gives pablo/pim-123.
