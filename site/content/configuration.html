Configuration

PABLO reads two kinds of YAML files: one global ~/.pablo/config.yaml with your defaults, and one file per project in ~/.pablo/projects/. A project can override any default, key by key.

Add a project

Run the wizard (it detects the repository if you run it inside one):

pablo project:new

It asks for the repository path, a name, the type (work, open-source or personal, used to filter tasks and pick models), the issue tracker and its details, whether you have a QA step, and an optional branch prefix. It shows the YAML and writes it to ~/.pablo/projects/ once you confirm. Or write the file by hand; the smallest useful one, for GitHub:

# ~/.pablo/projects/wallet-kit.yaml
name: wallet-kit
type: open-source
repo:
  path: ~/dev/wallet-kit
  primary_branch: main
issue_tracker:
  provider: github
  identity: your-github-login
  project_key: WK        # GitHub has no issue keys: this becomes the branch prefix (wk-45)

And a Jira project with a QA step and a CI gate to ignore:

# ~/.pablo/projects/acme-pim.yaml
name: acme-pim
type: work
repo:
  path: ~/Sites/acme/pim
  primary_branch: main
issue_tracker:
  provider: jira
  identity: you@acme.example
  project_key: PIM
  site: acme.atlassian.net
sync:
  auto_apply: true
testing:
  failure_signal: "A FIX"      # the Jira status QA moves the issue to when it fails
ci:
  ignore_checks: ["approval"]  # manual deploy gates that never finish

Check it with pablo project:list and pablo system:doctor (which now also checks the tracker's command-line tool). An invalid project file never takes the others down: PABLO skips it and says so everywhere. project:list and task:list print a warning, the doctor reports it as a ❌, the dashboard shows a banner, and the background job logs it on every run. A command that names that project (pablo sync:run wallet-kit, task:start --project wallet-kit) fails with the file's own error. Two files with the same name are both skipped until you rename one. With Orca, register the repository once with orca repo add ~/dev/wallet-kit; with OpenChamber there's nothing to do. Skip it with Orca and agents still run, headless. Both examples are in the repository: examples/acme-pim.yaml and examples/config.yaml.

Remove a project

pablo project:remove wallet-kit

It refuses while the project still has active tasks (close them first with pablo task:close). It deletes only the YAML file: worktrees and the rest of ~/.pablo/ stay. It also regenerates the agents, so a tracker no project uses any more stops being taught to them.

Global defaults

~/.pablo/config.yaml is created by the installer from examples/config.yaml. It holds the keys every project inherits, plus a few that only exist globally.

default_model: opencode-go/glm-5.3-flash
pr_description_locale: en
sync:
  strategy: rebase
  auto_apply: false
  interval_minutes: 720
state_polling:
  interval_minutes: 10
review:
  bot_whitelist: []
ci:
  ignore_checks: ["approval"]
# agent_runtime: claude-code        # global only, default: opencode
# agent_backend: openchamber        # global only, default orca
# models:                           # global only
#   work: anthropic/claude-opus-4
# hooks:                            # your own command, see Get notified
#   command: 'notify-send PABLO "$PABLO_TASK → $PABLO_TO"'

Keys a project inherits

When a project omits one of these keys, the global value applies. Only some keys have a built-in default for when the global file omits them too; the others are required in the project or in the global file. The installed config.yaml sets every required key, with the values shown below.

KeyBuilt-in defaultMeaning
default_modelrequired somewhereModel for agents (see below)
pr_description_localerequired somewhereLanguage of the pull request descriptions /pablo-commit-and-pr writes
branch_prefixnonePrefix added to every branch name, verbatim (write the slash yourself, e.g. pablo/)
sync.strategyrequired somewhere (installed config: rebase)rebase or merge
sync.auto_applyrequired somewhere (installed config: false)false: sync only reports
sync.interval_minutesrequired somewhere (installed config: 720)How often branches are synced
state_polling.interval_minutesrequired somewhere (installed config: 10)How often pull requests are checked
main_update.enabledtrueKeep the primary checkout up to date
main_update.interval_minutes60How often
testing.enabledtrueWhether the project has a QA step
review.bot_whitelistrequired somewhere (installed config: [])Bot accounts whose reviews count (login with or without its [bot] suffix)
ci.ignore_checksrequired somewhere (installed config: ["approval"])Checks to leave out of CI
hooks.commandnoneYour own shell command, run in the background when a task changes state or an agent's analysis is ready (see Get notified). A project setting it to null or "" turns it off for that project
hooks.statesevery stateOnly run the command for transitions into these states, e.g. [request-changes, testing-failed, ci-red, approved, closed]
hooks.agent_finishedtrueAlso run it when an auto-launched agent finishes

If a required key isn't set anywhere (and, for default_model, no models entry matches), loading the project fails with an error such as no value for sync.interval_minutes — set it in the project config or ~/.pablo/config.yaml.

Global-only keys

agent_runtime
opencode (default), claude-code or copilot: the program that runs the agents. Also settable with the PABLO_AGENT_RUNTIME environment variable. It changes the command the doctor requires (opencode, claude or copilot), what the installer generates and links, and which model ids default_model accepts. A first install sets claude-code for you when it finds Claude Code but no OpenCode. It sets copilot when it finds Copilot CLI but neither OpenCode nor Claude Code. See Choose an agent runtime.
agent_backend
The agent environment (ADE): orca (default), openchamber or headless. Also settable with the PABLO_AGENT_BACKEND environment variable. With openchamber, the doctor checks the openchamber command instead of orca; with headless (no agent environment: every agent runs in the background) it checks neither. A first install sets openchamber for you when it finds OpenChamber but no Orca; when it finds neither it keeps orca, whose runs fall back to headless until Orca is installed. OpenChamber only runs OpenCode: with agent_runtime: claude-code or copilot it is refused. See Choose an agent environment.
models
A model per project type, optionally per agent; see below. It used to be called default_model_by_type: a config.yaml still using that name fails to load until the key is renamed. pablo system:install renames it for you, and so does pablo update, which runs it.
dispatch.poll_concurrency
How many projects the background job polls at once (default 2, from 1 to 8; 1 polls them one after the other). Only the poll job overlaps, sync and main never do. Each extra project polled at once is one more gh and tracker caller on the same accounts, so keep it low: see Polling several projects at once. An invalid value never stops the background job: it says so in its log and polls one project at a time.
dashboard_port
The port of the dashboard (default 8321): pablo web and its background service listen on 127.0.0.1:<dashboard_port>. The installer sets it when 8321 is taken by another program; change it with pablo system:install --port <port> (or edit it here and restart the service).
dashboard_trusted_hosts
Extra host names the dashboard answers, besides 127.0.0.1 and localhost (default: none), for when you reach it through something that forwards to 127.0.0.1: a reverse proxy, an SSH tunnel, an /etc/hosts alias. A list of exact host names or IP addresses, without scheme, port or wildcard, e.g. [pablo.home.arpa]. It doesn't change where the dashboard listens. Read on every request, so no restart is needed; an invalid value makes the dashboard answer the loopback names only, and pablo web refuses to start with it.
scheduler.path
Extra directories put first on the PATH of the background services, for a tool pablo system:install doesn't find on your own PATH: a list (path: [~/tools/bin, /opt/acli/bin]) or one colon-separated string. A leading ~ stands for your home directory. Run pablo system:install again after changing it. See The services' PATH.
prune.keep_days
How many days of logs pablo system:prune keeps (default 10, at least 1): agent logs, the daily archives of the macOS service logs and the binary's caches of other versions are removed once older than that. The prune runs every day at 03:00. See What grows and how it's pruned.
shell_completion
false keeps pablo system:install (and so pablo update) from installing the shell completion, and removes an installed one. Set by pablo system:install --without-completion, back to true by --with-completion; unset means on.

Choose the agent model

The model is resolved when an agent is launched, and passed to the runtime as --model. The first one found wins:

  1. the agent's entry in the project's own models;
  2. the project's own default_model;
  3. the agent's own entry under the project's type in models;
  4. the model for the project's type in models (the type's default, when it lists agents);
  5. the global default_model;
  6. as a last resort, the model written in the generated agent file.
# ~/.pablo/config.yaml — expensive models only on work projects
models:
  work: anthropic/claude-opus-4
  open-source: litellm/glm-5.3-flash
  personal: opencode-go/glm-5.3-flash

Keys must be project types (work, open-source, personal); an unknown key is an error.

A model per agent

A type's value can also be a mapping of agent to model, to give one agent a different model. default is the model of the type's other agents; without it, they get the global default_model.

default_model: litellm/glm-5.3-flash
models:
  work:
    rebase-conflict-resolver: anthropic/claude-sonnet-5-5
    default: anthropic/claude-opus-5-5
  personal: litellm/deepseek-v4.1-flash

The agent keys are task-analyst, ci-analyst, pr-feedback, task-feedback and rebase-conflict-resolver (see Agents), plus default; an unknown key is an error. A project that sets its own default_model uses it for every agent its own models doesn't list: its type's per-agent models don't apply to it. Each model is checked against agent_runtime, like default_model.

A project file can set models per agent too, with its own models: a mapping of agent to model (the same agent keys, without default, since that is the project's default_model). They beat everything else, for that project only:

# ~/.pablo/projects/acme-pim.yaml
default_model: anthropic/claude-opus-5-5           # optional
models:
  rebase-conflict-resolver: anthropic/claude-sonnet-5-5

The format depends on agent_runtime. OpenCode takes a provider/model id, as above. Claude Code takes an alias (sonnet, opus, haiku) or a full model id such as claude-sonnet-5-5; a provider/model id is refused with an error when the project loads. Copilot takes its own dotted model ids, such as claude-sonnet-5.5 or gpt-5.3-codex; a provider/model id or a Claude Code name (sonnet, claude-sonnet-5-5) is refused, with the dotted form suggested. Under Claude Code and Copilot the generated agents carry no model, so the last step never applies.

Runtimes and agent environments

agent_runtime (OpenCode, Claude Code or GitHub Copilot CLI) and agent_backend (the agent environment, or ADE: Orca, OpenChamber or headless) are global-only keys, above. How to choose them, each one's setup, model ids and limits, and the fallback rules are on Runtimes & ADEs.

Project files

One YAML file per project in ~/.pablo/projects/, any file name. Create one with pablo project:new or by hand. Every key:

name: wallet-kit              # required, unique
type: open-source             # required: work | open-source | personal

repo:
  path: ~/dev/wallet-kit      # required: the primary checkout
  primary_branch: main        # required
  primary_remote: upstream    # optional, default "origin": the remote new branches
                              # start from and sync rebases onto, e.g. when origin
                              # is your fork (task branches are still pushed to
                              # their own remote, origin by default)

worktrees_root: ~/dev/wallet-kit-worktrees
                              # optional, default ~/.pablo/worktrees/<repo folder name>/

issue_tracker:
  provider: github            # required: github | jira | linear
  identity: your-login        # required: whose issues are "assigned to me"
                              # (informational for Jira, which uses your acli login)
  project_key: WK             # required. Jira/Linear: the issue key prefix.
                              # GitHub: the branch prefix (GitHub has no keys)
  site: acme.atlassian.net    # Jira only, optional: the Atlassian site for links
  repo: acme/upstream         # GitHub only, optional: where issues and pull requests
                              # live, when you work on a fork

confluence:
  space: PIM                  # Jira only, optional: where agents look for docs

sync:
  strategy: rebase            # rebase | merge
  auto_apply: false
  interval_minutes: 30
state_polling:
  interval_minutes: 10
main_update:
  enabled: true
  interval_minutes: 60

testing:
  enabled: true               # false: no QA step, approval is final
  failure_signal: qa-failed   # GitHub: a pull request label. Jira/Linear: an issue status.
                              # Without it, testing-failed never triggers by itself.
review:
  bot_whitelist: ["copilot-pull-request-reviewer"]   # GitHub Copilot's reviews
ci:
  ignore_checks: ["approval"]

startup_script: ~/scripts/pablo-setup.sh
                              # optional: bash script run once per task, next to
                              # task-analyst, in its own terminal
default_model: opencode-go/glm-5.3-flash
pr_description_locale: en
branch_prefix: pablo/

In repo.path, worktrees_root and startup_script, a leading ~/ (or a bare ~) is your home directory, read from HOME; PABLO stops with an error if HOME isn't set. ~user/ is not expanded: write that path in full.

ci.ignore_checks

A list of words. Any check whose name, workflow or context contains one of them is left out when PABLO decides whether CI is red or green. Use it for checks that never finish on their own, such as CircleCI manual approval gates, which stay pending (or “action required”) forever and would otherwise keep the task in draft. It's deliberately simple: a substring match.

Startup script

startup_script runs once per task when it starts, in parallel with task-analyst, in its own terminal that stays open as a shell afterwards, so you can see its output. Use it to install dependencies or prepare the worktree: it runs from the worktree's directory. It's launched in the background and never blocks pablo task:start. Once it exits, PABLO counts it as done and never runs it again on its own. It may only run again if PABLO relaunches a launch that never started, so keep it safe to re-run.

Branch names

Branches PABLO creates follow a fixed pattern, lowercased:

[branch_prefix][project-key]-[issue-id]
  • Jira and Linear: the issue's key, so PIM-123 becomes pim-123.
  • GitHub: the project's issue_tracker.project_key and the issue number: project_key: WK and issue #45 give wk-45.
  • Prompt tasks: the project key and a short slug of the prompt, such as wk-fix-callback-verification. If the prompt mentions a Jira or Linear key from one of your projects, that issue's name is used instead.
  • No title is added: the name is only those parts.
  • Duplicates: if the name is already taken, PABLO tries -2, -3, … until one is free. It never reuses or overwrites a branch.

With branch_prefix: pablo/, the issue above gives pablo/pim-123.

Validate your config

PABLO knows every key it reads, with the type and range of its value. Run pablo system:config:validate after editing a config file: it checks ~/.pablo/config.yaml and every file in ~/.pablo/projects/, changes nothing, and prints each problem with its key:

$ pablo system:config:validate
✅ /home/you/.pablo/config.yaml
❌ /home/you/.pablo/projects/wallet-kit.yaml
   ⚠️  ci.ignore_check is not a known key, ignored; did you mean `ci.ignore_checks`?
   ❌ sync.interval_minutes must be a whole number of minutes, at least 1, got 0

2 files checked: 1 error, 1 warning

It exits with 1 when there is an error, 0 when there are only warnings. --format=json prints the same report as JSON (shape). pablo system:doctor runs the same checks in its config lines.

Unknown keys: a warning
A key PABLO doesn't know, usually a typo, is ignored, so the value you meant isn't applied: with ci.ignore_check, the global ci.ignore_checks applies instead. The warning suggests the closest known key, or says where a key belongs when you put a global-only key (agent_backend) in a project file, or a project key (repo) in config.yaml. It's never an error, so a file written for a newer PABLO still loads.
Invalid values: an error
Intervals (*.interval_minutes, prune.keep_days) must be whole numbers, at least 1, and dispatch.poll_concurrency one from 1 to 8; booleans (sync.auto_apply, testing.enabled, …) must be true or false; lists (ci.ignore_checks, review.bot_whitelist, hooks.states, dashboard_trusted_hosts) must be lists, even of one item ([approval]); sync.strategy, type and issue_tracker.provider must be one of their values; a section (sync, repo, …) must be a mapping; dashboard_port must be a port. A key left empty (branch_prefix:) counts as unset.
Paths: an error, only here
repo.path must be a git checkout, an absolute startup_script must exist (a relative one runs from the task's worktree and isn't checked), and the parent of a worktrees_root you set must exist (the directory itself is created with the first worktree).

Loading applies the same rules, so every command behaves the same way:

  • An invalid value in a project file leaves that project out, like a missing key: the warning, the doctor and the dashboard banner name the file and the key, and the other projects keep running.
  • An invalid value in ~/.pablo/config.yaml, for a key projects inherit (the table above), stops every command, since it applies to every project. A global-only key (dashboard_port, dashboard_trusted_hosts, scheduler.path, prune.keep_days, claude_code.remote_control, shell_completion, dispatch.poll_concurrency) is refused only by the command that reads it (pablo web, system:install, system:prune, …), so a bad port doesn't stop the background job; a bad dispatch.poll_concurrency only makes it poll one project at a time. agent_runtime and agent_backend are checked by the doctor and the background job, as before.
  • Unknown keys and paths are not checked when loading. A warning every five minutes in the background job's log would be noise, and a repository on a disk that isn't mounted yet must not stop the other projects. system:config:validate and the doctor, which system:install and pablo update run, are where you see them.
