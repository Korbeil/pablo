Configuration

PABLO reads two kinds of YAML files: one global ~/.pablo/config.yaml with your defaults, and one file per project in ~/.pablo/projects/. A project can override any default, key by key.

Global defaults

~/.pablo/config.yaml is created by the installer from examples/config.yaml. It holds the keys every project inherits, plus a few that only exist globally.

default_model: opencode-go/glm-5.3-flash
pr_description_locale: en
sync:
  strategy: rebase
  auto_apply: false
  interval_minutes: 720
state_polling:
  interval_minutes: 10
review:
  bot_whitelist: []
ci:
  ignore_checks: ["approval"]
# agent_runtime: claude-code        # global only, default opencode (or copilot)
# agent_backend: openchamber        # global only, default orca
# default_model_by_type:            # global only
#   work: anthropic/claude-opus-4

Keys a project inherits

When a project omits one of these keys, the global value applies. Only some keys have a built-in default for when the global file omits them too; the others are required in the project or in the global file. The installed config.yaml sets every required key, with the values shown below.

KeyBuilt-in defaultMeaning
default_modelrequired somewhereModel for agents (see below)
pr_description_localerequired somewhereLanguage of the pull request descriptions /pablo-commit-and-pr writes
branch_prefixnonePrefix added to every branch name, verbatim (write the slash yourself, e.g. pablo/)
sync.strategyrequired somewhere (installed config: rebase)rebase or merge
sync.auto_applyrequired somewhere (installed config: false)false: sync only reports
sync.interval_minutesrequired somewhere (installed config: 720)How often branches are synced
state_polling.interval_minutesrequired somewhere (installed config: 10)How often pull requests are checked
main_update.enabledtrueKeep the main checkout up to date
main_update.interval_minutes60How often
testing.enabledtrueWhether the project has a QA step
review.bot_whitelistrequired somewhere (installed config: [])Bot accounts whose reviews count
ci.ignore_checksrequired somewhere (installed config: ["approval"])Checks to leave out of CI

If a required key isn't set anywhere (and, for default_model, no default_model_by_type entry matches), loading the project fails with an error such as no value for sync.interval_minutes — set it in the project config or ~/.pablo/config.yaml.

Global-only keys

agent_runtime
opencode (default), claude-code or copilot: the program that runs the agents. Also settable with the PABLO_AGENT_RUNTIME environment variable. It changes the command the doctor requires (opencode, claude or copilot), what the installer generates and links, and which model ids default_model accepts. A first install sets claude-code for you when it finds Claude Code but no OpenCode. It sets copilot when it finds Copilot CLI but neither OpenCode nor Claude Code. See Run the agents with Claude Code and with GitHub Copilot CLI.
agent_backend
orca (default), openchamber or headless. Also settable with the PABLO_AGENT_BACKEND environment variable. With openchamber, the doctor checks the openchamber command instead of orca; with headless (no agent development environment: every agent runs in the background) it checks neither. A first install sets openchamber for you when it finds OpenChamber but no Orca; when it finds neither it keeps orca, whose runs fall back to headless until Orca is installed. OpenChamber only runs OpenCode: with agent_runtime: claude-code or copilot it is refused. See Agent backends.
default_model_by_type
A model per project type; see below.
dashboard_port
The port of the dashboard (default 8321): pablo web and its background service listen on 127.0.0.1:<dashboard_port>. The installer sets it when 8321 is taken by another program; change it with pablo system:install --port <port> (or edit it here and restart the service).

Choose the agent model

The model is resolved when an agent is launched, and passed to the backend as --model. The first one found wins:

  1. the project's own default_model;
  2. the entry for the project's type in default_model_by_type;
  3. the global default_model;
  4. as a last resort, the model written in the generated agent file.
# ~/.pablo/config.yaml — expensive models only on work projects
default_model_by_type:
  work: anthropic/claude-opus-4
  open-source: litellm/glm-5.3-flash
  personal: opencode-go/glm-5.3-flash

Keys must be project types (work, open-source, personal); an unknown key is an error.

The format depends on agent_runtime. OpenCode takes a provider/model id, as above. Claude Code takes an alias (sonnet, opus, haiku) or a full model id such as claude-sonnet-5-5; a provider/model id is refused with an error when the project loads. Copilot takes its own dotted model ids, such as claude-sonnet-5.5 or gpt-5.3-codex; a provider/model id or a Claude Code name (sonnet, claude-sonnet-5-5) is refused, with the dotted form suggested. Under Claude Code and Copilot the generated agents carry no model, so step 4 never applies.

Run the agents with Claude Code

PABLO runs its agents with OpenCode by default. To use Claude Code instead, set it in ~/.pablo/config.yaml, then regenerate and relink:

agent_runtime: claude-code
default_model: sonnet

curl -fsSL https://getpablo.dev/installer | bash -s -- --runtime claude-code
                            # generates ~/.pablo/runtime/claude/agents.json, links the agents and the command
                            # (already installed: pablo system:install --runtime claude-code)
pablo system:doctor         # checks claude and the generated files
  • Global only. Every project uses the same runtime; there is no per-project setting.
  • Orca or headless. Agents run as claude -p in an Orca terminal, and as a Remote Control session headless, exactly where OpenCode would run. OpenChamber is not supported: it drives its own OpenCode server. pablo system:doctor reports the combination as an error and the dispatcher refuses to run with it; switch to agent_backend: orca or back to agent_runtime: opencode.
  • Your account and quota. Agents run with your own Claude Code login. With a Pro or Max subscription they share its usage limits with your interactive sessions, so keep an eye on them with busy projects.
  • Your settings, not your MCP servers. Agents load your Claude Code settings and hooks (Orca's, RTK's) but none of your MCP servers (--strict-mcp-config).
  • Sessions you can resume. Each run gets a session id chosen by PABLO; claude --resume <id> in the worktree reopens it.

Follow headless runs from claude.ai and the Claude apps

A run with no terminal (agent_backend: headless, Orca's and OpenChamber's fallback, the rebase-conflict resolver) starts as an interactive claude --remote-control session named pablo <agent> <worktree> instead of claude -p, so it shows up live in claude.ai/code and the Claude apps while it runs. It is still a background run that ends on its own:

  • A terminal from script. Interactive claude needs one; the command runs inside script (part of every Linux and macOS system). Its screen output goes to the run's log in ~/.pablo/agents/logs/.
  • It stops when the agent has answered. A Stop (and StopFailure) hook passed with --settings ends the session after the agent's answer, so the run finishes like a claude -p one. You can't continue it from the app afterwards: claude --resume <id> in the worktree still reopens it.
  • Same agent, same limits. Same model, session id and permission flags as claude -p, with only the launched agent passed inline in --agents (interactive claude takes no file there). Every agent, the resolver included, runs in dontAsk: nobody is there to answer a prompt.
  • The worktree is trusted first. PABLO adds a hasTrustDialogAccepted entry for the worktree to ~/.claude.json just before the launch.
  • Needs a claude.ai login on which your organization allows Remote Control.

To keep plain claude -p runs, switch it off in ~/.pablo/config.yaml (or export PABLO_CLAUDE_REMOTE_CONTROL=0):

claude_code:
  remote_control: false   # default: true

Without a generated agents.json or a script command, runs fall back to claude -p.

How the agent permissions translate is on Agents; what gets installed where is on Installation.

Run the agents with GitHub Copilot CLI

To use GitHub Copilot CLI instead, set it in ~/.pablo/config.yaml (or export PABLO_AGENT_RUNTIME=copilot), then regenerate and relink:

agent_runtime: copilot
default_model: claude-sonnet-5.5

curl -fsSL https://getpablo.dev/installer | bash -s -- --runtime copilot
                            # renders ~/.pablo/runtime/copilot/ and links the agents and skills into ~/.copilot/
                            # (already installed: pablo system:install --runtime copilot)
pablo system:doctor         # checks copilot and the generated files
  • Global only. Every project uses the same runtime.
  • Orca or headless. Agents run as copilot -p, in an Orca terminal or headless, like the other runtimes. OpenChamber is not supported, as with Claude Code: the doctor reports it and the dispatcher refuses to run.
  • Copilot model ids. Dotted ids such as claude-sonnet-5.5 or gpt-5.3-codex. A provider/model id (bring-your-own-model ids aren't supported) or a Claude Code name (sonnet, claude-sonnet-5-5) is refused when the project loads, with the dotted form suggested.
  • Your instructions, not your MCP servers. Agents load your custom instructions and hooks, but see only the built-in tools PABLO lists, and Copilot's built-in MCP servers are off.
  • Sessions you can resume. Each run gets a UUID chosen by PABLO; copilot --resume=<id> in the worktree reopens it.

How the agent permissions translate is on Agents; what gets installed where is on Installation.

Add a project

Run the wizard (it detects the repository if you run it inside one):

pablo project:new

It asks for the repository path, a name, the type (work, open-source or personal, used to filter tasks and pick models), the issue tracker and its details, whether you have a QA step, and an optional branch prefix. It shows the YAML and writes it to ~/.pablo/projects/ once you confirm. Or write the file by hand; the smallest useful one, for GitHub:

# ~/.pablo/projects/wallet-kit.yaml
name: wallet-kit
type: open-source
repo:
  path: ~/dev/wallet-kit
  primary_branch: main
issue_tracker:
  provider: github
  identity: your-github-login
  project_key: WK        # GitHub has no issue keys: this becomes the branch prefix (wk-45)

And a Jira project with a QA step and a CI gate to ignore:

# ~/.pablo/projects/acme-pim.yaml
name: acme-pim
type: work
repo:
  path: ~/Sites/acme/pim
  primary_branch: main
issue_tracker:
  provider: jira
  identity: you@acme.example
  project_key: PIM
  site: acme.atlassian.net
sync:
  auto_apply: true
testing:
  failure_signal: "A FIX"      # the Jira status QA moves the ticket to when it fails
ci:
  ignore_checks: ["approval"]  # manual deploy gates that never finish

Check it with pablo project:list and pablo system:doctor (which now also checks the tracker's command-line tool). With Orca, register the repository once with orca repo add ~/dev/wallet-kit; with OpenChamber there's nothing to do. Skip it with Orca and agents still run, headless. Both examples are in the repository: examples/acme-pim.yaml and examples/config.yaml.

Remove a project

pablo project:remove wallet-kit

It refuses while the project still has active tasks (close them first with pablo task:close). It deletes only the YAML file: worktrees and the rest of ~/.pablo/ stay. It also regenerates the agents, so a tracker no project uses any more stops being taught to them.

Project files

One YAML file per project in ~/.pablo/projects/, any file name. Create one with pablo project:new or by hand. Every key:

name: wallet-kit              # required, unique
type: open-source             # required: work | open-source | personal

repo:
  path: ~/dev/wallet-kit      # required: the main checkout
  primary_branch: main        # required
  primary_remote: upstream    # optional, default "origin": the remote sync and new
                              # branches use, e.g. when origin is your fork

worktrees_root: ~/dev/wallet-kit-worktrees
                              # optional, default ~/.pablo/worktrees/<repo folder name>/

issue_tracker:
  provider: github            # required: github | jira | linear
  identity: your-login        # required: whose issues are "assigned to me"
                              # (informational for Jira, which uses your acli login)
  project_key: WK             # required. Jira/Linear: the issue key prefix.
                              # GitHub: the branch prefix (GitHub has no keys)
  site: acme.atlassian.net    # Jira only, optional: the Atlassian site for links
  repo: acme/upstream         # GitHub only, optional: where issues and pull requests
                              # live, when you work on a fork

confluence:
  space: PIM                  # Jira only, optional: where agents look for docs

sync:
  strategy: rebase            # rebase | merge
  auto_apply: false
  interval_minutes: 30
state_polling:
  interval_minutes: 10
main_update:
  enabled: true
  interval_minutes: 60

testing:
  enabled: true               # false: no QA step, approval is final
  failure_signal: qa-failed   # GitHub: a pull request label. Jira/Linear: an issue status.
                              # Without it, testing-failed never triggers by itself.
review:
  bot_whitelist: ["copilot-pull-request-reviewer[bot]"]
ci:
  ignore_checks: ["approval"]

startup_script: ~/scripts/pablo-setup.sh
                              # optional: bash script run once per task, next to
                              # task-analyst, in its own terminal
default_model: opencode-go/glm-5.3-flash
pr_description_locale: en
branch_prefix: pablo/

ci.ignore_checks

A list of words. Any check whose name, workflow or context contains one of them is left out when PABLO decides whether CI is red or green. Use it for checks that never finish on their own, such as CircleCI manual approval gates, which stay pending (or “action required”) forever and would otherwise keep the task in draft. It's deliberately simple: a substring match.

Startup script

startup_script runs once per task when it starts, in parallel with task-analyst, in its own terminal that stays open as a shell afterwards, so you can see its output. Use it to install dependencies or prepare the worktree. It's launched in the background and never blocks pablo task:start. It may run again if PABLO relaunches a launch that never started, so keep it safe to re-run.

Branch names

Branches PABLO creates follow a fixed pattern, lowercased:

[branch_prefix][project-key]-[issue-id]
  • Jira and Linear: the issue's key, so PIM-123 becomes pim-123.
  • GitHub: the project's issue_tracker.project_key and the issue number: project_key: WK and issue #45 give wk-45.
  • Prompt tasks: the project key and a short slug of the prompt, such as wk-fix-callback-verification. If the prompt mentions a Jira or Linear key from one of your projects, that issue's name is used instead.
  • No title is added: the name is only those parts.
  • Duplicates: if the name is already taken, PABLO tries -2, -3, … until one is free. It never reuses or overwrites a branch.

With branch_prefix: pablo/, the issue above gives pablo/pim-123.
