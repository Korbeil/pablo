Task states

Every task is in exactly one of ten states. You move a task with two commands; the background poller moves it the rest of the way by watching CI, reviews and QA. This page lists every state and every rule behind the transitions.

The map

There's no todo state on purpose: a ticket nobody has started has no task, it only exists in your tracker.

Into draft: /pablo-commit-and-pr

The one and only way work enters (or re-enters) draft, allowed from in-progress, ci-red, request-changes, testing-failed, waiting-review and approved. It commits, pushes, opens the pull request as a draft if needed, then sets the state. A raw git push is never detected and never changes a state. The single other way in is a closed task whose pull request is reopened. How to use it: Ship your work.

What the poller watches

The poller only checks what makes sense for each state:

StateChecks
draftCI red, CI green
ci-redCI green
waiting-reviewCI red, reviews
request-changesreviews (feedback-addressed check)
approvedCI red
needs-testingQA failure signal
closedreopen (back to draft), merge
any statemerge, close without merging (even waiting)

CI

  • Red moves draft (or waiting-review) to ci-red. Green moves draft or ci-red to review.
  • Pending is not a signal: the task just stays where it is.
  • No checks at all counts as green, otherwise a project without CI could never leave draft.
  • Checks whose name matches ci.ignore_checks are left out.
  • If CI turns red during review (after a sync push, for example), the task goes to ci-red and comes back the usual way. The pull request never left “ready” on GitHub, so reviews given before the blip still count.

Reviews

From waiting-review, the poller reads the pull request's reviews and decides between approved and request-changes:

  • Your own reviews never count. Replying to a comment on your own pull request creates a review in your name; it shouldn't send you back to draft.
  • Bots are ignored, unless listed in review.bot_whitelist.
  • Only reviews after GitHub's last “ready for review” event count. An approval from a previous round doesn't leak into this one. (GitHub's summary verdict is not used: it has no timestamp.)
  • The latest review of each reviewer wins. Every review and every comment thread is read, however long the pull request: each reply to a comment is a review of its own, so a busy pull request can hold hundreds.
  • Resolved comments clear a comment review. A review whose comment threads were all resolved, and that carries no top-level body text, no longer counts as a changes signal — resolving is the reviewer's way of saying "addressed". A non-empty review body without a thread to resolve keeps counting, and resolving threads never withdraws an explicit “changes requested” verdict.
  • Any “changes requested” or plain comment review beats every approval. If someone took the time to write, you read it before QA.
  • Re-enters review when everything is addressed (🔁 only). While in request-changes, once pr-feedback has finished and no review signal stands anymore (every comment review resolved-cleared, no “changes requested”, no approval pending), the poller puts the pull request back to review itself: it marks it ready on GitHub and settles the task in waiting-review. Nothing is committed or pushed — address the feedback in the worktree and let the reviewers look again.

QA failure signal

From needs-testing, the task moves to testing-failed when the project's testing.failure_signal fires: a label added to the pull request (GitHub), or the issue reaching a status (Jira, Linear). It must be a new event, newer than both the task's entry into needs-testing and the last signal already handled. An old label never triggers, and a label that stays never triggers twice. PABLO never removes the label or touches the ticket.

Known gaps, on purpose

CI turning red during needs-testing, or during approved for projects without QA, doesn't move the task. A broken CI shows up at merge time anyway.

Projects without QA

With testing.enabled: false, an approved review leaves the task in ✅ approved until the merge closes it. Entering needs-testing is refused, including with pablo task:state or when resuming a paused task.

Pausing and manual moves

  • pablo task:waiting saves the state and pauses. Resuming restores the state and runs its usual actions (agents that only run once don't run again). Resuming into needs-testing keeps the original baseline, so QA signals that arrived during the pause are handled, not lost. Not allowed from request-changes or testing-failed.
  • pablo task:state <state> forces a state and runs the same actions as the automatic transition; --no-trigger only records it (except for waiting, which always remembers the previous state).
  • pablo task:attach <state> adopts an existing worktree: it only writes the record, launches nothing and flips nothing. Analytics see the state as entered at attach time.

How to use them: Managing tasks.

Launches that never start

Agent launches are fire-and-forget, so they never block a command. If no agent session appears for an agent-launching state (in-progress, ci-red, request-changes, testing-failed) within a short window, which happens when Orca hangs on a brand-new worktree, the poller fires the launches again, up to a few attempts, startup script included. In in-progress it also sets the Orca workspace name to the issue key. Then the normal checks run, so a ci-red task that turned green still moves on. You can always force it with pablo task:relaunch.
