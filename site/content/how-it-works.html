How it works

PABLO has two layers: the commands you run, and a background job that runs every 5 minutes, checks each project and does whatever is due. Agents run in your agent environment (ADE: Orca, OpenChamber or headless), and everything else is plain, deterministic code.

Two layers

Interactive
What you run: the pablo commands, the /pablo-commit-and-pr command (OpenCode, Claude Code or Copilot), and the agent sessions you open in Orca or OpenChamber.
Background
A scheduler (systemd user timer on Linux, launchd agent on macOS) runs pablo system:dispatch every 5 minutes, and pablo system:prune every day at 03:00.

The background job

On each run, the dispatcher:

  1. takes a global lock, so two runs never overlap (a second one exits immediately);
  2. checks the tools it needs. A problem with gh, with the runtime's command (opencode, claude or copilot), or an impossible agent setup (OpenChamber with Claude Code or Copilot) stops the run; a problem with a tracker tool or the ADE only produces a warning, and only the projects using that tool are affected;
  3. for each project, runs the jobs whose interval has elapsed since their last success: first every due sync, one after the other, then the due polls, a few projects at a time, then every due main update, one after the other.

A job's “last run” time is only saved when it succeeds, so a failure is retried on the next run. One project failing never blocks the others, and that includes its YAML file: a project file that doesn't load (invalid YAML, a missing or invalid key, a name another file already uses) only drops that project. Each run prints the file and its error on stderr, then dispatches the other projects and exits non-zero. An invalid ~/.pablo/config.yaml is different: it affects every project, so nothing runs. Adding or removing a project changes nothing in the scheduler: each project's cadence lives in its YAML file.

Polling several projects at once

Polling is mostly waiting on gh, git and the tracker commands, so the dispatcher polls up to dispatch.poll_concurrency projects at once (default 2; see Global-only keys). Each one runs in a child process of the same pablo (pablo internal:dispatch-job); the dispatcher keeps the global lock while they run and records their stamps and health itself, exactly as when it runs them one after the other.

  • Only polls overlap. Sync and main update write to git repositories (rebase, push, reset of the primary checkout), so they still run one at a time, sync before the polls and main after them: a project's own jobs keep their order and never overlap. Two projects on the same repository are never polled at the same time either.
  • Same requests, sooner. Polling at once never adds a request: each project makes the calls it always made, only the run ends sooner. It does send them closer together, and every project shares your gh account and tracker account. GitHub asks clients to avoid concurrent requests and limits bursts on top of the hourly quota (secondary rate limits), which is why the default is 2 and the maximum 8.
  • A rate limit slows the run down. When a project's poll fails on something that looks like a rate limit (or one of its tasks' checks does), that project fails alone and backs off as usual, and the projects still waiting in that run are polled one at a time, as with poll_concurrency: 1. Nothing is retried.
  • Output stays readable. Each project's lines are printed together once its poll ends, so the log groups them by project, in the order the polls finish.
  • Bounded. A poll still running after 10 minutes is stopped and counts as that project's failure, and no poll starts more than 10 minutes into the run: the ones left wait for the next run. One project's failure, crash or hang never blocks the others.

Set dispatch.poll_concurrency: 1 to poll one project after the other, in the dispatcher's own process, as before.

Health and back-off

The dispatcher records how each run and each job went, next to the stamps (see Storage):

  • per project and job: the last attempt, the last success, the last error (one line, cut at 300 characters) and how many times in a row it failed;
  • for the poll job, how many tasks' checks failed on its last run. A task whose check fails doesn't fail the job: the other tasks are still polled;
  • for the whole run: when it started and finished, and whether it went fine, had a failing job, or stopped on the tool check.

A job that fails twice in a row backs off instead of retrying every 5 minutes: it waits 5 minutes × 2failures − 1 after its last attempt (10, 20, 40 minutes…), never longer than its own interval. One success ends the back-off, and so does running the job by hand: pablo system:poll and pablo sync:run ignore the back-off and, when they work, reset the failure count (not pablo sync:run --dry-run, which proves too little).

pablo system:doctor shows all this in its scheduler section, and the dashboard shows a banner while a job is failing. Recording is best-effort: a problem writing these files never stops a run.

Because the dispatcher wakes up every 5 minutes, a job runs at the first wake-up after its interval has elapsed, not at the exact minute.

Agent environments (ADEs)

PABLO doesn't run agents itself. It hands them to the agent environment (ADE: Orca, OpenChamber or headless), exactly the way you would, and asks it which agents are busy. The ADE is chosen with the agent_backend config key (or the PABLO_AGENT_BACKEND environment variable).

The ADE decides where an agent runs; the runtime (agent_runtime: the agent CLI, OpenCode, Claude Code or Copilot CLI) decides what runs there: opencode run --agent <agent> '<prompt>' by default, or claude -p --agents ~/.pablo/runtime/claude/agents.json --agent <agent> --session-id <id> … -- '<prompt>' with Claude Code, or copilot --agent pablo-<agent> --session-id <uuid> … -p '<prompt>' with Copilot. Orca and headless run any of them; OpenChamber only runs OpenCode. How to choose both is on Runtimes & ADEs; this section shows what each ADE runs.

Orca (default)

# launch
orca terminal create --worktree path:<worktree> --title "pablo:<agent>" \
     --command "cd <worktree>; sh -c '…'" --json
#   the terminal starts, in the background:  opencode run -s ses_pablo<id> --agent <agent> '<prompt>'
#   then, once that session exists:          opencode -s ses_pablo<id>   (the TUI)
# wait for the end of a run (you quitting the TUI)
orca terminal wait --terminal <handle> --for exit --timeout-ms 3600000 --json
# who is working
orca worktree ps --limit 200 --json

On Linux the Orca CLI is orca-ide, the name Orca gives it there because orca is GNOME's screen reader; PABLO runs orca-ide on Linux and orca elsewhere (or Orca's ORCA_CLI_COMMAND when set). The launch runs in the background, so pablo task:relaunch cannot tell whether Orca took it: when Orca refuses or doesn't know the worktree within 15 seconds, the agent runs headless and the reason goes to ~/.pablo/agents/logs/orca-fallback.log.

Under OpenCode the tab shows the OpenCode TUI on the agent's session: you follow the analysis live, then carry on the conversation with the same agent and model. The TUI takes no agent or model of its own, hence the background opencode run that starts the session under an id PABLO picks; if that run fails before creating it (an unknown model, say), its error stays in the tab. The run counts as finished when you quit the TUI.

An agent that is working or running counts as 🏃 busy; anything else (idle, waiting for input) counts as 💭 waiting for you. Orca only knows repositories registered with orca repo add. Under Claude Code the terminal runs claude -p instead (copilot -p under Copilot), and Orca follows it through the hooks it installs in your Claude Code settings, as it does for your own sessions.

OpenChamber

Select it with agent_backend: openchamber in ~/.pablo/config.yaml or PABLO_AGENT_BACKEND=openchamber.

openchamber session create --dir <worktree> --title "pablo:<agent>"
openchamber session send --session <id> --dir <worktree> --prompt "<prompt>" --agent <agent>
openchamber session messages --session <id> --dir <worktree> --wait
openchamber session list --dir <worktree> --with-status

OpenChamber works from directories: no repository to register, no waiting for a workspace to appear. busy and retry count as 🏃, idle as 💭. If sending the prompt fails, PABLO logs the reason to ~/.pablo/agents/logs/openchamber-fallback.log and falls back to a headless run with the same model.

Headless

With agent_backend: headless, and whenever Orca or OpenChamber is unreachable or doesn't know the repository, PABLO runs the runtime's command (opencode run --agent <agent>, claude -p … --agent <agent> or copilot --agent pablo-<agent> … -p) in the background from the worktree, tracked with pid files in ~/.pablo/agents/. Under Claude Code a headless run is a Remote Control session by default, so you can follow it live from claude.ai/code and the Claude apps. Headless runs always count as busy (🏃) while they run, since they can't report being idle. Project startup scripts and the rebase-conflict resolver always use this path.

Follow headless OpenCode runs in the browser

Under OpenCode, headless runs go through OpenCode's background service, which also serves a local web interface listing every session, the agents' included, live. opencode pair prints a link to it:

$ opencode pair
  Open a link to connect. Links work once and expire in 5 minutes.
  http://127.0.0.1:49374/auth/connect/…

The link works once and expires after 5 minutes; the browser stays connected afterwards. Over SSH, forward the port first (ssh -L 49374:127.0.0.1:49374 <host>, with the port from the link), then open the link on your machine. From another device on your network, opencode service set hostname 0.0.0.0 makes the service listen beyond 127.0.0.1 (anyone on the network can then reach it with a pairing link). To carry on a session in the terminal instead: opencode -s <session> in the worktree (opencode session list shows the latest first).

What PABLO may change

PABLO never writes your code or a commit of its own, and never changes your tracker. The few git and pull request operations it performs, and the files it writes on your machine, are listed on What PABLO may change.

Design decisions

Command-line tools, no tokens

PABLO talks to every service through its own command-line tool, already logged in on your machine. There's no API key in its configuration and none should be added. When a tool isn't ready, PABLO shows that tool's own error. See Providers.

One timer for all projects

A single 5-minute dispatcher reads each project's intervals from its YAML file, instead of one scheduler unit per project. Adding a project is just adding a file.

A state machine, not an agent framework

The states are the ones a pull request goes through in a real team. Each state, its display and what runs on entering it live in one table in StateMachine.php; what the poller checks for each state lives in one table in Poller.php. The same entry handler is used by the poller, the commands and manual overrides, so the behaviour never diverges.

Why not OpenClaw?

OpenClaw's scheduled “heartbeat” would map well onto the background job, but it was ruled out: it's much heavier than needed (a persistent self-hosted gateway with messaging integrations versus a timer calling a few tools); its skills run with full privileges and no sandbox; and skills from its community registry have no integrity verification, a known supply-chain risk. On top of a working OpenCode setup, that wasn't worth it.
